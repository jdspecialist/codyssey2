\# 코드 설계 및 책임 분리



\## Quiz 클래스



개별 퀴즈 한 개를 표현한다.



\- 속성: question, choices, answer

\- show(): 문제와 선택지를 출력한다.

\- is\_correct(): 사용자 답과 정답을 비교한다.



\## QuizGame 클래스



게임 진행에 필요한 상태와 기능을 관리한다.



\- 속성: quizzes, best\_score

\- play\_quiz(): 퀴즈 출제와 결과 계산

\- add\_quiz(): 사용자 입력으로 새 퀴즈 등록

\- show\_quiz\_list(): 등록된 퀴즈 목록 출력

\- show\_best\_score(): 최고 점수 출력

\- save(): 현재 상태 저장 요청



\## 파일별 역할



| 파일 | 책임 |

|---|---|

| main.py | 프로그램 시작, 메뉴 선택, 종료 처리 |

| quiz.py | 퀴즈 한 개의 데이터와 동작 |

| game.py | 게임 진행, 퀴즈 관리, 점수 계산 |

| storage.py | JSON 파일 저장·불러오기·복구 |



\## 클래스를 사용한 이유



문제, 선택지, 정답을 Quiz 객체 하나로 묶어 관리한다.

게임 전체의 상태는 QuizGame에 모아 관리한다.

새로운 퀴즈를 추가해도 기존의 출력과 정답 확인 기능을 재사용한다.



\## 데이터 흐름



실행 → 저장 데이터 불러오기 → Quiz 객체 생성

→ 메뉴 선택 → 게임 상태 변경 → 파일 저장 → 종료



\## 시스템 아키텍처 분석 및 확장성 설계 (Scalability \& Design Review)



\### 초기 로딩 구조 분석

\- \*\*현재 구조\*\*: 프로그램 시작 시점(`main()`)에 `load\_state()`를 호출하여 `state.json`에 저장된 \*\*전체 퀴즈 데이터를 메모리(List 객체)에 한 번에 로드\*\*하는 구조를 채택하고 있습니다.

\- \*\*특징\*\*: 데이터 규모가 작을 때(수십\~수백 건)는 디스크 I/O 횟수를 최소화하여 빠른 응답 속도를 보장합니다.



\### 퀴즈 1,000개 규모에서의 목록 출력 전략

\- \*\*한계점\*\*: 1,000개의 퀴즈 목록을 한 번에 터미널에 출력(`print`)할 경우, 스크롤이 지나치게 길어져 가독성이 극도로 떨어지고 사용자가 원하는 정보를 찾기 어렵습니다.

\- \*\*개선 방안 (Pagination)\*\*: 

&#x20; - 사용자의 가독성과 조작 편의성을 위해 \*\*10개 단위(또는 페이지별)로 나누어 출력\*\*하는 페이징 기법을 도입해야 합니다.

&#x20; - 예: `\[1페이지: 1\~10번]`, `\[2페이지: 11\~20번]` 형태로 사용자에게 페이지 번호 입력을 받아 슬라이싱(`quizzes\[start:end]`)하여 출력하는 구조 설계.



\### 검색 기능 추가 시 대상 필드 설계

만약 퀴즈 검색 기능을 도입한다면 다음과 같은 필드를 대상으로 지정하는 것이 효율적입니다.

\*\*질문 내용 (`question`)\*\*: 키워드 기반 부분 일치 검색(Sub-string Matching)의 주된 대상. 사용자가 특정 개념(예: "변수", "반복문")이 포함된 문제를 빠르게 찾을 수 있도록 지원.

\*\*선택지 항목 (`choices`)\*\*: 특정 키워드가 보기 안에 포함된 퀴즈를 필터링할 때 보조 검색 필드로 활용.



\### 실제 측정 데이터 및 실행 시간

\- \*\*측정 환경\*\*: 로컬 파일 시스템 (`state.json`), 기본 5개 퀴즈 기준

\- \*\*실행 시간\*\*:

&#x20; - `load\_state()` 파일 읽기 및 파싱: \*\*0.001초 미만\*\*

&#x20; - `save\_state()` 전체 직렬화 및 임시 파일 교체(Atomic Write): \*\*0.005초 미만\*\*

\- 소규모 학습용 프로젝트 환경에서 디스크 I/O 및 객체 초기화 지연 없이 즉각적인 반응 속도를 보여줍니다.



\### JSON 전체 저장 방식의 대규모 확장성 한계

현재 구현된 JSON 전체 통째 저장 방식(`json.dump`)은 데이터가 수만\~수십만 건 이상으로 대규모화될 경우 다음과 같은 구조적 한계에 직면합니다.

1\. \*\*메모리 부하 (Memory Overhead)\*\*: 모든 데이터를 메모리에 상주시켜야 하므로 데이터가 커질수록 메모리 사용량이 비례하여 증가합니다.

2\. \*\*I/O 병목 현상 (I/O Bottleneck)\*\*: 사소한 데이터 변경(예: 점수 1점 갱신, 퀴즈 1개 추가)에도 \*\*전체 데이터셋을 직렬화하여 파일 전체를 다시 쓰기(Overwrite)\*\* 해야 하므로 디스크 I/O 부하가 커집니다.

3\. \*\*동시성 제어 부재 (Concurrency Issues)\*\*: 멀티스레드나 다중 프로세스 환경에서 파일 접근 시 Race Condition(경쟁 상태)이 발생하여 데이터 유실 위험이 존재합니다.

\- \*\*결론\*\*: 향후 대규모 서비스로 확장할 경우 파일 시스템 기반 저장소 대신 \*\*SQLite\*\* 등 경량 관계형 데이터베이스로의 전환이 필요합니다.
